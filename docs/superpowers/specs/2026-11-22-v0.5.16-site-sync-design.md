# v0.5.16 官网同步设计

## 意图

上游 `elkpi/frp-tun` 已发布 v0.5.16（tag 指向合并提交 `6c3e412`，核心变更 PR #35）。本站需要同步发行说明与版本指针，让 `/releases/v0.5.16/`、首页版本行、操作/配置文档与官网 Release 保持一致，并维持既有的契约与安全校验门禁。

## 目标

- 中英新建 `releases/v0.5.16.mdx`，slug 显式声明为 `releases/v0.5.16` / `en/releases/v0.5.16`。
- 发行说明按上游 Release 口径覆盖 `auto` 数据面、`hub_unencrypted`、`frp-tun pin`、混合部署、IPv6 动态前缀加固、`sync_port` 升级提示。
- 所有“当前版本”指针从 v0.5.15 更新到 v0.5.16（首页、releases 索引、OpenWrt、full-reference 字段字典说明，共 8 处）。
- 操作/CLI 文档补齐 `frp-tun pin` 与 `auto` 数据面说明；配置字典补齐 `data_plane`、`hub_unencrypted` 与 `sync_port` 默认值变更。
- 契约测试随新版本更新；`npm test`、`npm run check`、`npm run build`（含 prebuild 校验）全绿。

## 非目标 / 反目标

- 不在本轮创建官网 GitHub Release、上传资产或触发 Pages 部署；那属于单独审批的对外发布动作。
- 不宣称性能收益、非零 `SO_MARK` 支持或 OpenWrt 真机验证；明确保留“本地环回 E2E 通过、`-race` 由 CI 验证”的边界。
- 不改动闭源核心仓库，不把上游内部 spec 直接复制到公开站点。

## 约束

- 公开内容必须遵守 `scripts/validate-public-content.mjs` 的主机名/IP/密钥白名单与扩展名限制。
- 版本化发行说明必须显式写 `slug`（Astro github-slugger 会吞掉点号）。
- Starlight 要求每个中文页面有英文对应页；`validate-release-metadata.mjs` 要求发行说明具备规定章节和匹配的 version/slug。
- 资产下载 URL 指向 `elkpi/frp-tun-page` 的官网 Release（与 v0.5.15 一致），摘要以 `elkpi/frp-tun` 上游 Release 的 `checksums.txt` 为准。

## 方案选择

1. **沿用 v0.5.15 的“两提交”模式（推荐）**：第一笔提交新增中英发行说明 + 契约测试，第二笔提交更新全站版本指针与既有文档。与历史发布完全一致， cherry-pick 粒度清晰，便于回滚。
2. 单笔大提交同时改完所有内容：省事但混在一起，不符合“commit 粒度要足够细”的全局偏好。
3. 只改版本指针，不写发行说明：无法满足 `/releases/v0.5.16/` 可访问与契约测试要求。

选择方案 1。

## 实现要点（已定部分）

- 发行说明摘要和“已验证范围”直接复用上游 Release 的六项要点与验证边界；下载表使用上游已核对的资产名、链接与上 `checksums.txt` 一致的 SHA256。
- `checksums.txt` 自身摘要若上游 API 已提供 digest，则写入“已验证范围”；五个二进制摘要以清单文本而非 API 元数据为准。
- 操作文档在 `frp-tun apply` 与 `frp-tun down` 之间插入 `frp-tun pin`，并在末尾新增 `auto` 数据面章节；CLI 参考增加 `pin` 子命令编号，通过契约测试确认中英一致。
- 配置文档在 `site` 段模板增加 `data_plane` / `hub_unencrypted` 注释，并更新 `sync_port` 说明；既有 IP/主机白名单用 RFC 5737 地址。

## 留给实现者的部分

- 实际写文案时按中英全文逐句对照上游 Release，不新增未经证实的功能描述。
- 校验失败时以 `scripts/validate-*` 与契约测试的具体报错定位修正，不绕过门禁。
