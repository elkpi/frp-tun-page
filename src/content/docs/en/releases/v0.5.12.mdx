## Summary

- **Negative batch-count fallback**: Fixes the case where a negative count from batched `sendmmsg`/`recvmmsg` could not fall back to single-packet I/O. After a partially successful batch call, Bind and Endpoint no longer resend or stop early. Cancellation and illegal counts are covered.
- **Endpoint batch-write buffers**: Batch writes reuse buffers for the duration of one call, and honor cancellation before each chunk.
- **Production default unchanged**: Receive mode is separate from batched send capability. Production still defaults to batch receive; this release does not switch on small-packet receive mode.
- **Diagnostic samples, not a performance result**: The receive-mode comparison is diagnostic only. All 60 samples of a 1000 pps userspace WireGuard benchmark completed, but key metrics varied by more than 10% on one side. This release therefore does not claim a stable performance gain, and it did not run a higher load on that basis.
- **Resource targets unchanged**: The support target remains 128MB RAM / 32MB Flash. 64MB/16MB remains a stress-evaluation tier, not a supported claim.
- Previously validated capabilities and conclusions from [v0.5.11](/en/releases/v0.5.11/) and earlier remain in effect.

## Validated scope

- All five official architecture binaries were checked against the accompanying `checksums.txt`.
- Negative batch-count fallback, send boundaries after a partial batch success, and cancellation plus illegal counts are covered by the upstream release tests.
- All 60 samples of the 1000 pps userspace WireGuard diagnostic run completed. Key metrics varied by more than 10% on one side, so receive mode was not switched and the comparison is not a stable performance gain.
- Resource targets are unchanged: 128MB RAM / 32MB Flash remains the support target. Devices with 64MB/16MB memory remain a stress-evaluation tier, not a supported claim.

## Known limitations

- The receive-mode comparison is diagnostic only. Results that vary by more than 10% do not support a stable performance gain, and small-packet receive mode is not the production default.
- This release was not validated on physical devices, kernel WireGuard, live carrier paths, or nonzero `SO_MARK`.
- Devices with 64MB/16MB memory remain a stress-evaluation tier, not a supported claim.
- Cross-compiled assets are not a compatibility guarantee for specific hardware, sustained heavy load, nonzero `SO_MARK`, or complex NAT scenarios.
- The software has no automatic updates or availability SLA; see the [EULA](https://github.com/elkpi/frp-tun-page/blob/main/EULA.md).

## Upgrade

During a maintenance window, back up the existing configuration and binary and prepare an independent rollback path. Download the binary for the target architecture and verify its digest, then stop the service, replace the binary, and restart. Run `frp-tun doctor` to check status. When an enabled journal exists, restart restores its committed configuration; use `frp-tun apply` to change configuration. See [Upgrade & rollback](/en/operations/upgrade-rollback/).

## Rollback

Stop the service, restore the backed-up binary, restart, and check status. Reverting the binary is not the same as reverting configuration; consult the target version's release notes and journal behavior first.

## Withdrawal

For serious security or stability issues, maintainers will mark the public Release as withdrawn and publish a notice according to [SECURITY.md](https://github.com/elkpi/frp-tun-page/blob/main/SECURITY.md).
