## Summary

`frp-tun v0.5.3` focuses on end-to-end peer dialing symmetry for native QUIC P2P direct connectivity, resolving irreversible NAT traversal failures caused by unidirectional fixed initiation, alongside fixing CGNAT port-block endpoint freshness drops that stranded successful hole-punches in relay mode.

### Key Improvements

1. **CGNAT Port-Block NAT Freshness Fix**: For peers behind CGNAT port blocks, endpoints under the same peer IP authenticated by bidirectional QUIC encryption are admitted; failure drop logging now outputs precise drop predicates, completely resolving the defect where valid punches stayed stranded on relay;
2. **Native QUIC P2P Direct Dialing Symmetry (Peer-to-Peer)**: Introduces a dynamic single-initiator state machine where site roles determine default initiation (visitor dials, proxy accepts). After 3 consecutive terminal failures, the initiation direction automatically inverts and immediately triggers a fresh dial attempt, guarded by a 2-minute hysteresis window and auto-resetting on network changes or WAN renumbering;
3. **Dual-End Resident QUIC Listeners & Conflict Resolution**: Both visitor and proxy roles maintain resident listeners on loopback UDP sockets, allowing either peer to act as an acceptor. When concurrent dialing creates race conditions, candidate sessions are collected and deterministically converged by global SiteID lexicographical order (highest wins), gracefully terminating the loser without side effects;
4. **Initiator-Driven Stream Handshake Deadlock Elimination**: Re-engineers `authenticateWithOrder` so that connection direction (rather than static site role) dictates TLS/authentication write precedence, eliminating deadlocks where empty dialer streams caused acceptors to block indefinitely in `AcceptStream`;
5. **End-to-End `DialRole` Observability**: `carrier.Session` and `supervisor.Status` (top-level and `Peers[]`) expose `DialRole` (`"dialer"` / `"acceptor"`), and session establishment log lines output a `, dial=` tag;
6. **Strict Backward Compatibility & Seamless Fallback**: Wire protocol preserves strict canonical encoding compatibility; relay transport (STCP/XTCP via frps) retains full legacy visitor/proxy semantics and private relay Preferred Hub prioritization.

## Upgrade

1. Back up existing gateway configuration (e.g. `/etc/frp-tun/config.toml`);
2. Stop the running daemon:
   ```bash
   systemctl stop frp-tun
   ```
3. Replace the binary and set executable permissions:
   ```bash
   chmod +x frp-tun_v0.5.3_amd64
   mv frp-tun_v0.5.3_amd64 /usr/local/bin/frp-tun
   ```
4. Start the service and inspect runtime status:
   ```bash
   systemctl start frp-tun
   ```

---

## Rollback

If unexpected behavior occurs post-upgrade:
1. Stop the service: `systemctl stop frp-tun`;
2. Restore the previous verified binary to `/usr/local/bin/frp-tun`;
3. Clean up residual policy routes and interfaces (if any): `ip link delete frp-tun:0 2>/dev/null || true`;
4. Restart the previous daemon version.

## Revocation

In the event of critical security flaws or kernel panics, maintainers will mark the release as `REVOKED — DO NOT USE`, remove affected binary assets, and issue a security bulletin via [SECURITY.md](https://github.com/elkpi/frp-tun-page/blob/main/SECURITY.md).
