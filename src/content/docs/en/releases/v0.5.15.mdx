## Summary

- **New TUN + QUIC data plane**: Adds the site-level `site.data_plane = "tun-quic"` setting. For a single direct peer, IP packets move from the kernel TUN straight to authenticated QUIC Datagrams without an additional WireGuard layer. Leaving the field unset keeps WireGuard over QUIC (the default `wg-quic`), so existing configurations behave as before.
- **Authentication and isolation**: `tun-quic` adds a bidirectional site private-key proof bound to the current QUIC connection on top of existing site authentication. Both ends must use the same data plane and pass an equal-length MTU probe; inbound and outbound IP packets are filtered against approved peer prefixes. This mode does not support relay fallback, Stream transport, automatic MTU adjustment, or experimental duplication.
- **Dynamic IPv6 prefixes**: Prefixes are advertised only over an active, authenticated QUIC control stream and are governed by leases, policy routes, nftables, and source filtering. Revocation retains isolation protection rather than falling back to a normal egress path.
- **Lifecycle fix and compatibility**: Fixes a failure to start again after `down` leaves the journal in a stopped state. Existing configuration digests and journals remain compatible.
- **Upgrade notice**: `tun-quic` uses a new protocol number. Both ends must upgrade to v0.5.15 to interoperate; older previews (preview1–preview5) are incompatible. The `wg-quic` protocol number is unchanged.
- Previously validated capabilities and conclusions from [v0.5.14](/en/releases/v0.5.14/) and earlier remain in effect.

## Validated scope

- SHA256 digests for all five architecture binaries were verified against the upstream `checksums.txt`. The manifest digest is `8f52ed5742cba51f1097fd6aecf35371072a6edfe5d318e92a173ac05701a0b9`.
- Upstream tests cover loopback QUIC authentication, dynamic-prefix advertisement and revocation, firewall-update failure shutdown, lease expiry, and recovery from a synthetic older journal.
- `tun-quic` is a single-peer direct data plane. Sessions are rejected without matching modes, a completed private-key proof, and a passing MTU probe; no application data is parsed or forwarded otherwise.
- Resource targets are unchanged: 128MB RAM / 32MB Flash remains the support target. Devices with 64MB/16MB memory remain a stress-evaluation tier, not a supported claim.

## Known limitations

- `tun-quic` does not support relay fallback, multiple peers, Stream transport, automatic MTU adjustment, or experimental duplication. Both ends must upgrade to v0.5.15; older previews (preview1–preview5) are incompatible.
- This release includes no dedicated privileged-environment end-to-end 1000 pps comparison for a real kernel TUN with QUIC, no nonzero `SO_MARK` routing validation, and no real-device OpenWrt validation. It claims neither performance gains nor lower resource usage.
- Cross-compiled assets are not a compatibility guarantee for specific hardware, sustained heavy load, nonzero `SO_MARK`, or complex NAT scenarios.
- The software has no automatic updates or availability SLA; see the [EULA](https://github.com/elkpi/frp-tun-page/blob/main/EULA.md).

## Upgrade

During a maintenance window, back up the existing configuration and binary and prepare an independent rollback path. Download the binary for the target architecture and verify its digest, then stop the service, replace the binary, and restart. Run `frp-tun doctor` to check status. When an enabled journal exists, restart restores its committed configuration; use `frp-tun apply` to change configuration. To try `tun-quic`, run `down` first and start only after both ends have been upgraded and configured consistently. See [Upgrade & rollback](/en/operations/upgrade-rollback/).

## Rollback

Stop the service, restore the backed-up binary, restart, and check status. Reverting the binary is not the same as reverting configuration; consult the target version's release notes and journal behavior first.

## Withdrawal

For serious security or stability issues, maintainers will mark the public Release as withdrawn and publish a notice according to [SECURITY.md](https://github.com/elkpi/frp-tun-page/blob/main/SECURITY.md).
