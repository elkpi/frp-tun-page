## Summary

- **Full-path attribution**: Adds a local two-ended benchmark. The path is MemoryTUN plaintext, userspace WireGuard encryption, LoopbackBind and Bridge, a real QUIC datagram on an independent socket, then decrypt-and-deliver on the peer. The unique-sequence ledger checks plaintext length and compares the IP header, identity region, and payload byte for byte. Truncation or corruption is no longer counted as a successful delivery. Samples carry stage markers, and input digests are checked before publication.
- **Diagnostic counts**: The diagnostic socket records real `WriteMsgUDP` calls and `UDP_SEGMENT` segment counts. A calibration test with two real sends shows the counters are accurate, separating GSO capability from actual batching. Diagnostic samples must carry both actual counts, and the relationship between them is checked.
- **Sample scheduling**: The full workload matrix is mandatory. The measure, profile, and diagnostic phases are isolated, and each sample runs in its own process. A result is published only after identity, hash, and count checks pass; a failure cancels the remaining samples. GSO on and off are sampled as a pair.
- **Test fix**: The supervisor fake-clock race test asserts the IPv4 budget from the remaining deadline, not from the number of waiters.
- **Below the optimization threshold**: All 60 official samples of the 1000 pps full path completed. The only stable, guardrail-passing case is receive-direction 1400B (rx/1400B), with a CPU improvement of 9.42%, below the 10% threshold. In the GSO on/off comparison, the stable group's CPU difference was 0% to 8%, also below the production threshold (at least 10% CPU or at least 20% allocations). This machine's loopback showed no actual multi-segment sends. Production therefore still defaults to batch receive, this release does not switch on small-packet receive mode, and it does not claim a stable performance gain. The production data path is unchanged.
- **Resource targets unchanged**: The support target remains 128MB RAM / 32MB Flash. 64MB/16MB remains a stress-evaluation tier, not a supported claim.
- Previously validated capabilities and conclusions from [v0.5.12](/en/releases/v0.5.12/) and earlier remain in effect.

## Validated scope

- All five official architecture binaries were checked against the accompanying `checksums.txt`.
- All 60 official samples of the 1000 pps full path completed. Truncated or corrupted plaintext is rejected and is not counted as a successful delivery.
- Receive-direction 1400B is the only stable, guardrail-passing case. Its CPU improvement is 9.42%, below the 10% threshold. The stable group in the GSO on/off comparison differed by 0% to 8% CPU, below the production threshold. This machine's loopback showed no actual multi-segment sends.
- Measurements are from this machine: Linux 5.15 aarch64, `GOMAXPROCS=2`, and MemoryTUN. They are not OpenWrt or x86 device results. The five-architecture cross build only shows that the binaries compile.
- Resource targets are unchanged: 128MB RAM / 32MB Flash remains the support target. Devices with 64MB/16MB memory remain a stress-evaluation tier, not a supported claim.

## Known limitations

- A 9.42% CPU change is below the 10% threshold and is not a stable performance gain. Small-packet receive mode is not the production default, and the production data path is unchanged.
- The GSO comparison's 0% to 8% CPU difference is also below the threshold. This loopback did not perform actual multi-segment sends, so it does not show a GSO benefit.
- Profiles still show system calls dominating (flat 53% to 58%). Endpoint reads account for about 2% to 4% cumulative, and LoopbackBind sends for about 3% to 14% cumulative. The cumulative stacks overlap, so those two figures must not be added.
- The results do not represent OpenWrt, x86, or a live carrier path. Nonzero `SO_MARK` and complex NAT were not measured in this release.
- Devices with 64MB/16MB memory remain a stress-evaluation tier, not a supported claim.
- Cross-compiled assets are not a compatibility guarantee for specific hardware, sustained heavy load, nonzero `SO_MARK`, or complex NAT scenarios.
- The software has no automatic updates or availability SLA; see the [EULA](https://github.com/elkpi/frp-tun-page/blob/main/EULA.md).

## Upgrade

During a maintenance window, back up the existing configuration and binary and prepare an independent rollback path. Download the binary for the target architecture and verify its digest, then stop the service, replace the binary, and restart. Run `frp-tun doctor` to check status. When an enabled journal exists, restart restores its committed configuration; use `frp-tun apply` to change configuration. See [Upgrade & rollback](/en/operations/upgrade-rollback/).

## Rollback

Stop the service, restore the backed-up binary, restart, and check status. Reverting the binary is not the same as reverting configuration; consult the target version's release notes and journal behavior first.

## Withdrawal

For serious security or stability issues, maintainers will mark the public Release as withdrawn and publish a notice according to [SECURITY.md](https://github.com/elkpi/frp-tun-page/blob/main/SECURITY.md).
