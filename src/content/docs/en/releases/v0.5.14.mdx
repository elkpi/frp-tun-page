## Summary

- **In-process ciphertext handoff**: Userspace WireGuard no longer passes ciphertext over loopback UDP. It now hands ciphertext to the data pump through in-process per-peer queues in the same process. Kernel mode still uses UDP handoff and keeps port pinning. Queues are dispatched per peer (a pair of queues with capacity 1024 each), avoiding cross-peer interleaving; re-registering the same peer identity after removal receives a fresh queue generation.
- **Status and shutdown fixes**: In-process devices report listen and status ports as 0. When the port is 0, the firewall no longer adds a UDP destination-port drop rule, and startup logs no longer claim a UDP listen port. A write to a full queue still blocks, but bind close, peer-port close, and pump cancellation all unblock it.
- **Fixture comparison**: The handoff fixture was rerun 40 times at `GOMAXPROCS=2` (five runs for each of four scenarios). Relative to loopback handoff, CPU medians changed by tx 64B −27.7%, tx 1400B −11.8%, rx 64B −30.2%, and rx 1400B −17.1%. Only the tx 1400B and rx 64B groups had both-side relative MAD below 10%; the other two groups varied more. These numbers come from a fixture, not production wiring, and they do not prove the default path passed a production-wiring sample threshold.
- **Resource targets unchanged**: The support target remains 128MB RAM / 32MB Flash. 64MB/16MB remains a stress-evaluation tier, not a supported claim.
- Previously validated capabilities and conclusions from [v0.5.13](/en/releases/v0.5.13/) and earlier remain in effect.

## Validated scope

- The userspace WireGuard path hands ciphertext in-process through per-peer queues; kernel mode keeps UDP handoff and port-pinning behavior.
- In-process devices report a status port of 0. When the port is 0, no UDP destination-port drop rule is added, and related startup logging and shutdown behavior follow in-process device semantics.
- The handoff fixture completed 40 samples at `GOMAXPROCS=2` (five runs for each of four scenarios). The tx 1400B and rx 64B groups had both-side relative MAD below 10%; the tx 64B and rx 1400B groups showed higher relative MAD and are not treated as a stable gain.
- Official release binaries and their corresponding SHA256 digests are provided with the accompanying `checksums.txt`.
- Resource targets are unchanged: 128MB RAM / 32MB Flash remains the support target. Devices with 64MB/16MB memory remain a stress-evaluation tier, not a supported claim.

## Known limitations

- Fixture comparison results do not directly equal production-wiring gains. Only two of the four scenarios met both-side relative MAD below 10%, and the production-wiring 40-sample threshold was not completed, so this release must not claim a stable speedup on the default path.
- This release does not include real-device OpenWrt or nonzero `SO_MARK` validation. Behavior on complex NAT, live carrier paths, and specific hardware loads still requires target-environment measurement.
- Cross-compiled assets are not a compatibility guarantee for specific hardware, sustained heavy load, nonzero `SO_MARK`, or complex NAT scenarios.
- The software has no automatic updates or availability SLA; see the [EULA](https://github.com/elkpi/frp-tun-page/blob/main/EULA.md).

## Upgrade

During a maintenance window, back up the existing configuration and binary and prepare an independent rollback path. Download the binary for the target architecture and verify its digest, then stop the service, replace the binary, and restart. Run `frp-tun doctor` to check status. When an enabled journal exists, restart restores its committed configuration; use `frp-tun apply` to change configuration. See [Upgrade & rollback](/en/operations/upgrade-rollback/).

## Rollback

Stop the service, restore the backed-up binary, restart, and check status. Reverting the binary is not the same as reverting configuration; consult the target version's release notes and journal behavior first.

## Withdrawal

For serious security or stability issues, maintainers will mark the public Release as withdrawn and publish a notice according to [SECURITY.md](https://github.com/elkpi/frp-tun-page/blob/main/SECURITY.md).
