> **Applicable version: technical preview (v0.5.3).** Production security best practice: restrict configuration file permissions to `0600` (`chmod 600 config.toml`) to prevent unauthorized local users from reading cryptographic credentials.

`frp-tun` utilizes standard TOML syntax. The full parameter dictionary and sanitized production template are documented below:

```toml
schema_version = 1

# 1. Local Site Configuration
# ==============================================================================
[site]
id = "site-a"                         # Unique site identifier (Required, globally unique across network)
networks = ["198.51.100.0/24"]        # Local LAN subnets (CIDR list advertised to peers)
tunnel_address = "198.51.100.1/32"    # Local WireGuard point-to-point virtual tunnel IPv4 address (Required)
role = "proxy"                        # Role: "proxy" (passive listener) or "visitor" (active dialer)
allow_relay = true                    # Allow fallback to STCP relay when direct P2P fails (default: true)
mtu = 1420                            # WireGuard MTU (default: 1420, valid range 576~9000, must match across all peers)

# Optional: IPv6 Tunnel & Dynamic Prefix Synchronization
[site.ipv6]
enabled = false
tunnel_address = "2001:db8:1::1/128"
lan_interfaces = ["br-lan"]
dynamic_source = false
max_active_prefixes = 16
max_history_prefixes = 256

# ==============================================================================
# 2. Peer Site Configuration
# ==============================================================================

# declare each peer with successive [[peers]] array entries instead.
[peer]

# Optional: Multi-Path QoS Probing

enabled = false                       # Enable dynamic QoS probing

probe_timeout = "2s"                  # Probe packet timeout threshold (valid range 50ms~60s)

switchback_holddown = "30s"           # Stabilization observation holddown before switching back (valid range 1s~3600s)

# ==============================================================================
# 7. Private Relay Hub (Server Side)
# ==============================================================================
# Configure on sites acting as relay hubs; Spoke-side egress candidates are
# declared under [peer.private_relay].
[private_relay]
enabled = false                       # Allow carrying end-to-end encrypted WireGuard traffic for other site pairs
pairs = []                            # Authorized relay pairs, e.g. [["site-a", "site-b"]] (requires enabled = true and both ends configured as peers)
max_sessions = 8                      # Maximum concurrent relay sessions (valid range 1~64)
queue_bytes = 65536                   # Per-session relay queue size in bytes (valid range 4096~4194304)
bytes_per_second = 8388608            # Per-session rate limit in bytes/second (valid range 16384~1073741824)

# ==============================================================================
# 8. Logging & Diagnostics
# ==============================================================================
[log]
to = "console"                        # Log output destination: "console" or file path
level = "info"                        # Log level: "trace", "debug", "info", "warn", "error"
max_days = 3                          # Log file retention days
max_size = "10MB"                     # Log file rotation size threshold
max_backups = 3                       # Number of rotated log archives to retain
```

## Field Notes

- **STUN discovery targets**: when `p2p.stun_server` is unset, frp-tun probes NAT type and public port mappings against a built-in list of public STUN servers (full list in the outbound disclosure below); symmetric-NAT port prediction relies on the same samples. When set, the custom target is probed ahead of the built-in list, which remains as fallback samples. The `p2p.stun_servers` list key is validated but not yet wired into the probing engine in v0.5.2 (kept for forward compatibility); effective targets are decided by `p2p.stun_server` plus the built-in list. The two keys are mutually exclusive.
- **Two-stage hole-punch coordination**: `p2p.nathole_coordinator` only selects the preferred mechanism; the other mechanism is attempted automatically as a fallback stage. Budgets are controlled independently by `nathole_frp_timeout` and `nathole_native_timeout`; on per-stage timeout, punching proceeds to the next stage.
- **Multi-peer topologies**: use `[peer]` for a single peer; for three or more sites in a Hub-Spoke mesh, declare successive peers with the `[[peers]]` array. Public UDP listen ports default to `p2p.listen_port + index`, or can be set explicitly per peer via `peer.listen_port` (must be unique across peers).
- **P2P pre-shared secret fallback**: the P2P handshake secret is resolved in the order `peer.shared_secret` → `peer.shared_secret_file` → `frp.shared_secret` → `frp.shared_secret_file`, so multi-peer deployments may assign a dedicated secret per peer.
- **Legacy key aliases**: `p2p.keepalive_period` and `p2p.accept_grace` are legacy aliases of `p2p.quic_keepalive_period` and `p2p.accept_grace_after_failed_punch`, honored only when the new keys are unset.

## Built-in STUN Targets & Outbound Disclosure

To support security review and compliance auditing, this page discloses every third-party address that frp-tun connects to out of the box. During the native hole-punching stage, frp-tun sends standard STUN Binding requests (UDP port 3478; hostnames resolved to IPv4 addresses via DNS) to the following public STUN servers:

| Built-in target | Operator |
| --- | --- |
| `stun.miwifi.com:3478` | Xiaomi |
| `stun.chat.bilibili.com:3478` | Bilibili |
| `stun.cloudflare.com:3478` | Cloudflare |
| `stun.easyvoip.com:3478` | Public STUN service |

Outbound boundaries:

- Beyond the table above, frp-tun contains no other built-in third-party connections: frps signaling and relay addresses come from `[frp].server_addr`, while direct-hole-punching and private-relay targets are user-configured peers;
- UPnP/PCP port-mapping discovery only communicates with the local LAN gateway device and never touches third-party public hosts;
- The binary contains no telemetry, version checks, or analytics reporting;
- The built-in targets cannot be removed through configuration; environments with strict egress control should allow or block the hostnames above at the firewall level.
