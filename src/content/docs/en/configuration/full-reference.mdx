> **Applicable version: technical preview (field dictionary aligned with v0.5.17).** Production security best practice: restrict configuration file permissions to `0600` (`chmod 600 config.toml`) to prevent unauthorized local users from reading cryptographic credentials.

`frp-tun` utilizes standard TOML syntax. The full parameter dictionary and sanitized production template are documented below:

```toml

# 1. Local Site Configuration
# ==============================================================================
[site]

networks = ["198.51.100.0/24"]        # Local LAN subnets (CIDR list advertised to peers)

role = "proxy"                        # Role: "proxy" (passive listener) or "visitor" (active dialer)
allow_relay = true                    # Allow fallback to STCP relay when direct P2P fails (default: true)

# ==============================================================================

# listen_port_range = "53000-53999"    # Optional direct-port drift range (empty by default, port stays fixed; drifts only after sustained direct failures, never while stable)

manage_firewall = false               # Authorize daemon to open external firewall port

nathole_coordinator = "frp"           # Preferred NAT hole-punching coordinator: "frp" (default, frps-signaled) or "native" (local QUIC engine); the other mechanism is automatically used as fallback stage
nathole_frp_timeout = "10s"           # Hole-punch budget for the frp-coordinated stage (default 10s, valid range (0s,60s])
nathole_native_timeout = "10s"        # Hole-punch budget for the native stage (default 10s, valid range (0s,60s])

# when unset, a built-in list of public STUN servers is used — see the outbound disclosure below)

# stun_servers = ["stun.example.com:3478", "stun-alt.example.com:3478"] # Target list (up to 8 entries; validated but not yet wired into probing in v0.5.2)

enabled = false                       # Enable dynamic QoS probing

probe_timeout = "2s"                  # Probe packet timeout threshold (valid range 50ms~60s)
rtt_ratio_threshold = 1.3             # RTT switchover threshold ratio (valid range 1.05~10.0)
rtt_min_diff = "15ms"                 # Absolute RTT difference switchover threshold (default 15ms, valid range 1ms~10s)
loss_diff_threshold = 0.05            # Packet-loss difference switchover threshold (default 0.05, enabled when set above 0, valid range 0.01~1.0)
switchback_holddown = "30s"           # Stabilization observation holddown before switching back (valid range 1s~3600s)
# experimental_duplication = false    # Experimental: duplicate traffic across primary and standby paths, trading bandwidth for resilience against transient loss

# ==============================================================================
# 7. Private Relay Hub (Server Side)
# ==============================================================================
# Configure on sites acting as relay hubs; Spoke-side egress candidates are
# declared under [peer.private_relay].
[private_relay]
enabled = false                       # Allow carrying end-to-end encrypted WireGuard traffic for other site pairs
pairs = []                            # Authorized relay pairs, e.g. [["site-a", "site-b"]] (requires enabled = true and both ends configured as peers)
max_sessions = 8                      # Maximum concurrent relay sessions (valid range 1~64)
queue_bytes = 65536                   # Per-session relay queue size in bytes (valid range 4096~4194304)
bytes_per_second = 8388608            # Per-session rate limit in bytes/second (valid range 16384~1073741824)

# ==============================================================================
# 8. Logging & Diagnostics
# ==============================================================================
[log]

level = "info"                        # Log level: "trace", "debug", "info", "warn", "error"
max_days = 3                          # Log file retention days
max_size = "10MB"                     # Rotation size (default 10MB; 0 disables size-based rotation)

disable_print_color = false          # Disable console color (default false; applies only when to is console; file logs are never colored)
```

## Field Notes

- **STUN discovery targets**: when `p2p.stun_server` is unset, frp-tun probes NAT type and public port mappings against a built-in list of public STUN servers (full list in the outbound disclosure below); symmetric-NAT port prediction relies on the same samples. When set, the custom target is probed ahead of the built-in list, which remains as fallback samples. The `p2p.stun_servers` list key is validated but not yet wired into the probing engine in v0.5.2 (kept for forward compatibility); effective targets are decided by `p2p.stun_server` plus the built-in list. The two keys are mutually exclusive.
- **Two-stage hole-punch coordination**: `p2p.nathole_coordinator` only selects the preferred mechanism; the other mechanism is attempted automatically as a fallback stage. Budgets are controlled independently by `nathole_frp_timeout` and `nathole_native_timeout`; on per-stage timeout, punching proceeds to the next stage.
- **Multi-peer topologies**: use `[peer]` for a single peer; for three or more sites in a Hub-Spoke mesh, declare successive peers with the `[[peers]]` array. Public UDP listen ports default to `p2p.listen_port + index`, or can be set explicitly per peer via `peer.listen_port` (must be unique across peers).
- **P2P pre-shared secret fallback**: the P2P handshake secret is resolved in the order `peer.shared_secret` → `peer.shared_secret_file` → `frp.shared_secret` → `frp.shared_secret_file`, so multi-peer deployments may assign a dedicated secret per peer.
- **Legacy key aliases**: `p2p.keepalive_period` and `p2p.accept_grace` are legacy aliases of `p2p.quic_keepalive_period` and `p2p.accept_grace_after_failed_punch`, honored only when the new keys are unset.
- **Tunnel MTU adjustment**: `p2p.mtu_adjust` has been available since v0.5.7 and defaults to `suggest`. The sender still probes the single-datagram payload limit on its own. This field only decides what happens when that confirmed limit stays away from the current tunnel `mtu`: record a suggestion, apply a new MTU, or ignore it. The value must stay unchanged for 10 minutes with no session or path change. The suggestion is the largest tunnel MTU that still fits in one frame: the inner packet is padded to 16 bytes, then a 32-byte WireGuard transport header and a 4-byte frame header are added. A confirmed limit of 1404 suggests 1360, not 1380. Values below 1280 are not suggested, and this release does not raise MTU.
  - `suggest`: writes one log line and exposes `suggested_mtu` in `status` and `perf`. The same value is reported only once. It does not change the running configuration.
  - `auto`: uses the same controlled commit as a manual `frp-tun apply` (journal, rollback on failure, and rebuild). Automatic changes are at least 30 minutes apart, and that cooldown survives a session change. It changes the running configuration and the journal. When an enabled journal already exists, restart restores that commit, not the old `mtu` still written in the file.
  - `off`: no observation and no action.
  - A session or path change clears an unfinished 10-minute window and the `suggest` duplicate filter. The new path must be observed for a fresh 10 minutes.
  - Since v0.5.17, when both peers support two-end MTU negotiation, the negotiated result takes precedence over unilateral adjustment; `off` disables only unilateral observation, not negotiation.
- **Two-end MTU negotiation (v0.5.17)**: after a direct path is established, the two ends exchange advertisements over the authenticated control stream. The effective MTU is the smaller of both advertisements and the current path-derived ceiling, lower only, with a floor of 1280; it is hot-applied without rebuilding the interface or interrupting traffic. New results within a 5-minute cooldown are recorded and the latest is applied when the cooldown expires. Within one config file, `mtu` in `site` and `peer` sections must match; the two machines may differ (for example 1420 and 1360), and both interfaces then use the smaller value. With no path confirmation on a completely unreachable network, MTU is never lowered automatically. `status` exposes `effective_mtu`, `mtu_source` (`negotiated` or `config`), `mtu_advertise`, and `suggested_mtu`.
- **Direct port drift range (v0.5.17)**: `p2p.listen_port_range` is empty by default, which keeps the port fixed. When configured, a drift happens only after at least three consecutive direct failures lasting at least 60 seconds and one further failed retry; it never drifts while a connection is stable. Drifts are at least 30 minutes apart and capped at five per 24 hours, with the count persisted in the journal across restarts; drift is disabled while a portmapper is active, and the old port is kept for 120 seconds. The range must not overlap `listen_port`, a peer listen port, or the IPv6 `sync_port`. With `manage_firewall = true`, the whole range is allowed in one rule. `status` exposes `listen_port_drifts_24h`, which is only the number of successful drifts in 24 hours, not a switch.
- **Console color**: `log.disable_print_color` defaults to `false`. Set it to `true` to turn off console color. It matters only when the log destination is `console`; logs written to a file are not colored.

## Built-in STUN Targets & Outbound Disclosure

To support security review and compliance auditing, this page discloses every third-party address that frp-tun connects to out of the box. During the native hole-punching stage, frp-tun sends standard STUN Binding requests (UDP port 3478; hostnames resolved to IPv4 addresses via DNS) to the following public STUN servers:

| Built-in target | Operator |
| --- | --- |
| `stun.miwifi.com:3478` | Xiaomi |
| `stun.chat.bilibili.com:3478` | Bilibili |
| `stun.cloudflare.com:3478` | Cloudflare |
| `stun.easyvoip.com:3478` | Public STUN service |

Outbound boundaries:

- Beyond the table above, frp-tun contains no other built-in third-party connections: frps signaling and relay addresses come from `[frp].server_addr`, while direct-hole-punching and private-relay targets are user-configured peers;
- UPnP/PCP port-mapping discovery only communicates with the local LAN gateway device and never touches third-party public hosts;
- The binary contains no telemetry, version checks, or analytics reporting;
- The built-in targets cannot be removed through configuration; environments with strict egress control should allow or block the hostnames above at the firewall level.
